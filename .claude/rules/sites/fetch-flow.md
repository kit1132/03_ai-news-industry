# ソース取得フロー

## 取得手順

各ソースの取得は以下の順序で試行する。

1. **プライマリURLをWebFetchで取得**
2. 403 / 429 / タイムアウトの場合 → **代替URLがあればWebFetchで試行**
3. それでも失敗した場合 → **WebSearchで `site:ドメイン 検索キーワード 当年` を実行**
4. `site:` 検索で結果0件の場合 → **`site:` を外して `検索キーワード 当年` で再検索**
5. すべて失敗した場合 → ダイジェストに「取得不可（手動確認推奨）」と記載

## 403 を記録する前の判定順序（2026-08-06 追加）

**403 を取得障害として台帳に記録する前に、必ず次の順序で判定する。**

1. **まず WebFetch を試す。成功したなら障害として記録しない。** 本文が取れているソースを障害として登録してはならない
2. WebFetch が失敗した場合に限り `curl -sS -o /dev/null -w "%{http_code}" --max-time 25 <URL>` を実行する。
   `curl` の役割は**ゲートウェイ拒否とオリジン403の切り分けだけ**であり、取得可否の判定ではない
   - **ゲートウェイ拒否**: `curl` が exit 56 / `CONNECT tunnel failed, response 403` を返す。実行環境のネットワーク許可リスト外。
     **サイト側が復旧しても解消しない。** 解消するのは環境（Environment）の Allowed domains にそのドメインが追加されたときだけで、
     この設定はリポジトリからは変更できない（kit の UI 操作が必要）
   - **オリジン403**: HTTP レスポンスとして 403 が返る。サイト側のブロック。**許可リスト追加では解決しない**ので WebSearch 運用を継続する
3. 2 の分類とともに `IMPROVEMENT-BACKLOG.md`「既知の取得障害」へ記録する

⚠️ **`curl` の 403 は WebFetch の可否を代表しない。** 2026-08-03 に `github.com` 配下3 URL で
`curl` が一律 HTTP 403 を返す一方、**同一セッションの WebFetch は本文取得に成功する**事例が確認されている
（01_ai-news-Master の週次復旧チェック）。`curl` の結果だけで記録すると、
**実際には毎日取得できているソースを障害として登録してしまう**。

⚠️ **ネットワークポリシーの変更は新規セッションにのみ反映される。** 変更前に開始したセッションは古いポリシーを
保持したまま動くため、許可ドメイン追加の直後に同じセッションで確認しても拒否のままになる。
判定が食い違ったときはセッションの開始時刻を先に疑う。

**本節が実際に効いている例**: `daily-sources.md`「LLM API 料金」項では、`ai.google.dev` が許可ドメイン追加で復旧して
WebFetch 一次に戻った一方、`openai.com` / `platform.openai.com` は許可リスト追加後もオリジン403のままで WebSearch を
継続している。この2つを区別できないと、後者に対して復旧チェックを繰り返す空振りが続く。

本節は 01_ai-news-Master の B-021（2026-08-06 採用）を移植したもの。

## 恒久リダイレクト（301 / 308）を検出したときの扱い（2026-08-07 追加）

**登録ソースの URL が 301 / 308 を返したら、それは取得障害ではなく「ソース定義の陳腐化」である。**
`IMPROVEMENT-BACKLOG.md`「既知の取得障害」には書かない。

1. **判定**: WebFetch がリダイレクト検出を返したら、
   `curl -sS -o /dev/null -w "%{http_code} %{redirect_url}" --max-time 25 <URL>` で転送先を確認する。
   302 / 307（一時的）は対象外で、本節は恒久リダイレクトだけを扱う
2. **ソース定義を書き換える**: `daily-sources.md` の URL 欄を転送先に差し替える提案を台帳の「提案中」に起票する。
   既に転送先を扱う提案があれば、そこへ統合する（新規に別 ID を立てない）
3. **転送先の到達可否は別軸で記録する**: 転送先に到達できない場合、**転送先ホスト**をゲートウェイ拒否／
   オリジン403として「既知の取得障害」に1行記録する。**URL の陳腐化と到達性を1行に混ぜない**
4. **移設先が旧ソースの範囲を覆っているか確認する**: 恒久リダイレクトは統合を伴うことが多く、
   旧 URL の担当範囲が転送先で変わる。代替ソースを立てる場合は、
   **旧ソースにあって代替に無い情報**を `daily-sources.md` の備考に明記する

⚠️ **障害と混ぜたときの実害が他リポで2件出ている。**

- 2026-08-07・01: `developers.openai.com/codex/changelog` → `learn.chatgpt.com/docs/changelog`（308）。
  ゲートウェイ拒否として台帳に登録したため、サイト側の復旧を待つ形になっていた
- 2026-08-06・02: `release-plan/2026wave1/microsoft-copilot-studio/planned-features` → `aka.ms/MCStoM365Roadmap`（301）。
  「Learn MCP の誤応答」として障害登録し、**原因確定まで10日**かかった

**恒久リダイレクトはサイト側が復旧しても解消しない。** 復旧チェックではなくソース定義の更新で閉じる。
本リポジトリは年次レポート系で URL が改編されやすいため、**404 と同様に「移設された可能性」を先に疑う**。

⚠️ **「取得不能」で止めない。** リダイレクト先が読めない場合も、本ファイル冒頭の取得手順3（WebSearch）は有効である。
**ダイジェストに「取得不能」と書くのは WebSearch まで試して失敗したときだけ**にする（取得手順5）。

本節は 01_ai-news-Master の 2026-08-07 追加分を移植したもの。

## フォールバック発生時の記録ルール

フォールバック（手順2以降）を使用した場合、リポジトリルートの **`IMPROVEMENT-BACKLOG.md`「既知の取得障害」セクションを更新する**。ダイジェストの改善メモに書くのは「変化があったもの」だけ。

- **新規の障害**（台帳にない URL）: 台帳に以下の形式で1行追加し、ダイジェストの改善メモにも「障害の変化」として1行記載する

  ```
  - <ソース名 / URL>: <403/429/timeout>（初出 YYYY-MM-DD / 最終確認 YYYY-MM-DD）→ 回避策: <成功した方法 / なし（取得不可・手動確認推奨）>
  ```

- **既知の障害**（台帳にある URL）: 台帳の「最終確認」日付を更新するのみ。**ダイジェストには書かない**
- **復旧**（台帳で障害扱いの URL が正常取得できた）: 台帳の該当行の行末に `→ 復旧（YYYY-MM-DD）` を追記し、ダイジェストの改善メモに「障害の変化」として記載する。行は削除しない
- **回避策が安定している長期障害**: `daily-sources.md` の取得方法欄を回避策ベースに書き換える提案を、台帳の「提案中」に起票する（既に同趣旨の提案があれば回数を +1 するだけ）

## WebSearch利用時の注意事項

- `site:` オペレータは非対応の場合がある。結果0件なら必ず `site:` を外して再検索する
- WebSearchに日付フィルタ機能はない。クエリに年（例: `2026`）を含めて新しい結果を優先する
- インデックス反映に数時間〜数日のラグがある。速報性が必要な情報には限界がある
- WebSearch結果はURLとスニペットのみの場合がある。必要に応じて結果内のURLをWebFetchで追加取得する
