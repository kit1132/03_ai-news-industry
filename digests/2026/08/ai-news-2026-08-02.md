### 1. 令和8年版情報通信白書で国内企業の生成AI利用が86.4%に達した — 「導入率が低い」前提は使えなくなる

**要点**: 総務省の白書で企業の生成AI業務利用が **86.4%**（前年度 55.2%）、個人の利用経験が58.8%（同 26.7%）と出た。国内の課題は「まだ入っていない」から「入っているが組織的に使えていない」へ移った。

**詳細**: 公表は 7/24 で、調査は2026年1〜2月に日本・米国・ドイツ・中国の4カ国で実施されている。

- 企業: 生成AIを1つ以上の業務で利用する割合が日本 86.4%（2024年度 55.2%）
- 企業の方針: 「積極的に活用」または「領域を限定して活用」を定めている割合は日本 68.9%（前年 49.7%）。米国 90.9%・ドイツ 91.6%・中国 98.1%
- 個人: 利用経験率は日本 58.8%（2024年度 26.7%）。米国とドイツが 75.6%、中国が 93.6%
- 業務変革で「組織的な取組はない」と回答した割合は日本 **27.0%**、米国 1.4%、ドイツ 4.9%、中国 2.6%

国際比較で日本が明確に劣後しているのは利用率そのものではなく、組織的な取組の有無である。導入率で日本の遅れを説明する提案は数字が裏づけを失う一方、「利用は広がったが業務変革の体制が無い企業が4社に1社」という定量根拠が新たに使えるようになった。7/24 公表を本日まで9日間捕捉できておらず、本日の catch-up 収録にあたる。

### 2. DeepSeek が V4 Flash を単価据え置きのまま更新した — OpenAI の80%値下げでも追いつけていない

**要点**: DeepSeek が 7/31 に V4 Flash の再学習版を出し、単価 $0.14／$0.28 を据え置いたまま知能指数を40→**50** へ上げた。前日ハイライトの GPT-5.6 Luna 80%値下げ後でも、タスク単価はなお約60%安い。

**詳細**: 設計は変えず再ポストトレーニングだけで改善しており、価格は前版から動いていない。

- Artificial Analysis Intelligence Index 50（旧版 40）。自社上位の V4 Pro を6点上回り、GPT-5.6 Luna（max）の51 に1点差
- 価格: 入力 $0.14／出力 $0.28（100万トークンあたり・据え置き）。キャッシュヒットは $0.0028 で98%引き

### 3. OpenAI が次期モデルファミリー Astra を公表した — 次世代は数時間〜数日走る多エージェント前提になる

**要点**: OpenAI が 8/1 に、未公開の次期ファミリー **Astra** が10年以上未解決だった数学・理論計算機科学の10問を解いたと公開した。単発応答ではなく数時間〜数日走らせる前提の設計で、米政府の公開前レビューを通る最初のモデルになる。

**詳細**: 内部版が生成した結果を、機械検証可能な形で外部に出している。

- 対象領域: von Neumann 代数、球充填、回路計算量、Ramsey 理論など10件。いずれも10年以上（多くはそれ以上）進展が無かった問題
- 検証: 全結果に Lean 4 の証明証明書を添付し、249ページの原稿とあわせて GitHub で公開。要した API 計算コストは約 $2,000
- 設計: 複数のサブエージェントを並列に起動・調整して成果を統合し、計画・実行・検証・修正を長時間継続する
- 位置づけ: GPT-6 として出すか GPT-5 系列に収めるかは未定。Altman はワシントンで議員向けにデモ済み

エージェント運用の想定時間が「1リクエスト数分」から「数時間〜数日」へ延びると、コスト試算・監視・権限設計の前提がいずれも変わる。EO 14409 の30日レビュー枠組み（下記・未公表）が最初に適用される対象でもあり、公開時期は規制側の進捗にも左右される。

## 開発者ツール

### GCC が LLM 由来の重要コード寄与を拒否する方針を採用 — 線引きは著作権上の「約15行」
GCC ステアリングコミッティが AI ポリシーを公表した。Linux を支えるコンパイラ本体が、生成物由来のコードを著作権上の理由で明示的に締め出したことになる。次回見直しは2027年初頭に予定されている。

- 対象: ChatGPT / Gemini / GitHub Copilot 等の出力そのものに加え、人間が後から編集・書き直したものも、最終的な寄与が生成物に基づく限り拒否される
- 線引き: GNU プロジェクトのメンテナ指針にある「法的に重要（legally significant）」の閾値で、コード・テキストで約15行
- 例外: 些細な変更と、メンテナが受け入れを選んだテストケース
- 許容される用途: アイデアの議論、既存コードの理解、不案内な領域の学習、一般的な調査

OSS への寄与を伴う開発体制では、エージェント利用可否がプロジェクト単位で分岐する。寄与先のポリシー確認を開発フローに組み込む必要がある。

### Supabase がコーディングエージェント評価ベンチを OSS 公開 — Skills の有無で成績差が出る
Supabase が `supabase/evals` を Apache-2.0 で公開した。Claude Code / Codex / OpenCode を実際の Supabase タスクで採点する仕組みで、公開リーダーボードと日次監視の社内回帰スイートを兼ねる。評価タスクはスキーマ構築・Edge Function のデバッグ・壊れた RLS ポリシーの修正など実務に近いものが並ぶ。

- Build 段階の素点は Opus 5 と Kimi K3 が100%
- Skills を併用すると Sonnet 5 が78%→100%、GPT-5.6 Sol が89%→100%、GPT-5.4 mini が78%→89%
- ドキュメント参照量は Codex / GPT-5.6 が1シナリオあたり約8ページ、Claude Code は約2ページ

モデルの素の能力よりも、Skills などの文脈供給の有無で差が埋まる構図が実測で出ている。エージェント導入提案では、モデル選定より社内ドキュメント整備の優先度が高いことの根拠に使える。
