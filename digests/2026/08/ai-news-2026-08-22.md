### 1. Anthropic Python SDK が v1.0 へ — `temperature` で出力を制御していた実装は書き直しになる

**要点**: 8/20 公開。HTTP 層が `httpx` から `httpx2` へ移り、Messages メソッドの `temperature` / `top_p` / `top_k` と旧 Text Completions API が削除された。サンプリング指定で出力を揃えていた既存コードは、そのままでは v1.0 に上げられない。

**詳細**: 削除・変更されたのは長期の非推奨面と HTTP 層で、いずれも移行作業を伴う。

- HTTP 層: `httpx` から `httpx2`（API 互換のメンテナンス継続フォーク）へ移行。カスタムの `http_client` / `Timeout` / transport は `httpx2` 側のオブジェクトで組み直す。`DefaultHttpxClient` ヘルパーは変更なし。`httpx` にパッチを当てるトレーシング・モックのライブラリを使っている場合は起動時に `httpx2.alias_httpx()` を呼ぶ
- 必要 Python: 3.10 以上
- 削除されたもの: 旧 Text Completions API、Messages メソッドの `temperature` / `top_p` / `top_k`、tool runner のクライアント側 `compaction_control`
- 非同期クライアント: `.with_raw_response` の結果に `await response.parse()` が必要になった
- `AnthropicBedrock`: AWS リージョン未設定時に `us-east-1` へ既定で落ちるのをやめ、エラーを送出するようになった

⚠️ **サンプリング系パラメータの削除は、モデル側の制御が `effort` に一本化された流れの帰結にあたる**。07-24 収録の Claude Opus 5 で「`effort` が主要な制御手段」と明記され、`thinking: disabled` が effort `xhigh` / `max` で 400 を返す破壊的変更が入っていた。SDK 側はその前提を v1.0 で確定させた形になる。移行の全差分は公式の v1 migration guide に before / after 付きで載っている。

### 2. Claude Security が Mythos 5 で Enterprise に公開ベータ — 追加課金プランなしで脆弱性スキャンが使える

**要点**: 8/21 公開。Claude Enterprise の管理コンソールから有効化でき、**スキャンは既存プランのトークン利用として課金**される。セキュリティ用 AI の導入判断が「別製品を買うか」から「既存契約内で設定を変えるか」へ移った。

**詳細**: 同日の告知は4本立てで、提供面・資金・アクセス制度が同時に動いた。

- Claude Security への Mythos 5 投入: コードベースを走査して脆弱性を検出しパッチを提案する。対象は Claude Enterprise、状態は公開ベータ、有効化は管理者が admin console で行う。**別建ての料金アドオンは無い**
- パートナー製品への組み込み: セキュリティベンダーが自社製品に Mythos 5 を統合する。利用者が触れるのはパッチやアラートといった防御側の出力のみで、モデルへの直接アクセスは伴わない。提供時期の明示は無く、関心のあるベンダーは登録フォームから申し込む
- Defender Advantage Fund（0xDAF）: オープンソースのセキュリティ向けに **$35M 分の Claude クレジット**を配る。用途は脆弱性の修正・スキャンとパッチの自動化・実験的手法で、まず少数の大型パイロット助成から始める。初回の交付先は数週間内に公表
- Cyber Verification Program の拡大: Opus / Sonnet でセーフガードを緩める既存制度を、より広い dual-use 能力まで広げる。Mythos クラスへのアクセスは「その後」とされ、詳細は数週間内

⚠️ **08-06 収録のスキル・プラグインのセキュリティスキャン（beta）と同じ「Enterprise の管理コンソールで有効化する検査機能」の系列**にあたるが、あちらが持ち込み資産の検査であるのに対し本件は自社コードの脆弱性検出で、対象範囲が広い。課金がトークン従量である以上、提案時の見積もりはシート数ではなくスキャン対象のコード量から立てる必要がある。

### 3. GitHub Copilot が Slack と Teams で共有エージェントに — 個人の私的作業からチームの共同作業へ

**要点**: 8/21 に両方が公開プレビュー。`@GitHub` メンションで開始したセッションが**チームに共有**され、専用の code channel で差分を見ながら全員で方向づけできる。エージェント利用が「一人が私的に回すもの」から「会話ログに残る共同作業」へ変わる。

**詳細**: 2本は同日・同形式の告知だが、対象プランと課金が異なる。

- Slack 版: `@GitHub` メンションでコードや GitHub 上の活動に答え、バグ報告のトリアージ・既存 issue の更新・新規 issue の作成とラベル付けを行う。元の会話にノイズを足さないよう**専用の code channel を切って作業を隔離**し、依頼者が会議中や移動中でも非同期で進む。対象は **GitHub Copilot Business / Enterprise** で、利用は既存の Copilot エンタイトルメントに算入される
- Teams 版: 議論の最中に `@GitHub` でセッションを開始し、同じく専用の code channel で進捗を追う。Teams で始めた作業はセキュアなクラウドサンドボックス内で非同期に継続し、結果はターミナル・GitHub Copilot アプリ・任意の IDE から受け取れる。対象は**有料の Copilot プラン**だが、**クラウドエージェントのセッションとサンドボックスの利用は AI クレジットを消費**し、従量課金の予算設定が組織の消費を統制する。利用には Teams 用 GitHub アプリの導入と GitHub アカウント連携、管理者によるクラウドエージェント／サンドボックス機能の有効化が要る
- 共通の統制: リポジトリ管理者は**エージェントが書いた PR のマージに追加承認を要求**でき、人間のレビューを挟んだまま出荷できる

⚠️ **課金の当たり方が2製品で違う点が提案時の分岐になる**。Slack 版は既存エンタイトルメント内に収まるが、Teams 版はサンドボックス利用が AI クレジットの従量消費になるため、席数だけでは費用が読めない。08-20 収録の Copilot for JetBrains の `managed-settings.json` による中央統制と合わせ、**GitHub 側の統制語彙が IDE からチャットプラットフォームへ広がった**週にあたる。

- https://github.blog/changelog/2026-08-21-the-new-github-copilot-experience-in-slack
- https://github.blog/changelog/2026-08-21-shared-agentic-work-with-github-copilot-in-microsoft-teams

- GitHub Code Quality の有効化変更が監査ログに載るようになった — GitHub が 8/20 に3つのイベントを追加した。`repo.code_quality_enabled`（リポジトリで有効化）・`repo.code_quality_disabled`（無効化）・`repo.code_quality_updated`（有効なリポジトリの設定変更）で、いずれも対象リポジトリ・変更者・時刻を記録し、監査ログ API から照会できる。**Code Quality の課金は有効なリポジトリのアクティブコミッター数で数える**ため、有効化の履歴がそのまま費用の説明材料になる。対象は GitHub Enterprise Cloud（data residency 版を含む）と GitHub Team。08-19 収録の組織横断トレンドタブ・08-21 収録の Actions 専用パスに続き、Code Quality まわりが3日連続で更新された。
  - https://github.blog/changelog/2026-08-20-track-github-code-quality-enablement-changes-in-the-audit-log
